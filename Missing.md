## Test assets and policy decisions

- **Test oracle is incorrectly coupled to the firmware image:** `expected_class` currently comes from the firmware's hard-coded prompt/class tables, and firmware computes the ModelOut `pass` field. Changing a recording set, prompt order, or expected label therefore requires rebuilding the application image. Move the oracle to the host: generate a manifest containing session, utterance, expected class, source WAV, and first/last AudioIn timeslot; make firmware emit only observed inference data; and join ModelOut with the manifest in a post-playback test runner. If expectations must be visible in the SDS extension, generate a separate sparse `ExpectedClass` playback stream with one record per inference at the matching timeslot. Retain an explicit audio timeslot/range in ModelOut until SDS extension issue #266 exposes record-header timeslots.
- **Partially resolved — speech recordings:** 63 Moonshine ZipVoice source utterances (20 selected model words plus one out-of-vocabulary prompt, across three synthetic voices) are assembled into three natural speaker-session WAV/SDS pairs under `speech-app/test/recordings`, with 500 ms pauses and a manifest. `banana` is explicitly expected to be rejected as `UNKNOWN`. These enable deterministic functional tests. Real human speakers recorded through the AppKit microphone are still required for acceptance testing, with consent/license and speaker metadata.
- **Resolved — model/corpus vocabulary alignment:** runtime inspection confirmed the recovered WordCNN has the 51 spelling classes stored in `word_cnn.pt`, from `a` through `no`; it does not have `_unknown_`. The SDS positive prompts are a 20-word subset of those classes. `banana` tests confidence-based rejection, whose threshold still requires calibration.
- **Blocking — exact training-run provenance:** upstream documents a reproducible recipe: all words synthesized with 15 ZipVoice voices, real examples and `_unknown_` speech mined from MLCommons People's Speech, a speaker-independent split, and waveform/SpecAugment augmentation. It also provides the default 20 robot-command vocabulary and scripts that generate manifests. However, generated `data/` and checkpoint-run manifests are gitignored, so the exact clip IDs, speaker split, random state, augmentation history, and dataset snapshot behind the shipped 51-class spelling checkpoint cannot be reconstructed byte-for-byte from the repository. The checked-in model is the 51-class spelling model; no trained checkpoint for the documented 20-command-plus-`_unknown_` recipe was found. Our SDS corpus is an independent fixture, not training-set parity evidence.
- **Partially resolved — audio frontend and segmentation:** the Moonshine portable frontend is integrated and converts PCM16 to the model's 64×128 Slaney log-mel tensor; a deterministic energy segmenter uses the 500 ms fixture gaps and feeds every isolated utterance to ExecuTorch. FVP processed all 63 utterances without a transport, segmentation-count, inference, or timeout error. Golden tensor parity against Moonshine's `features.py` remains required. The Board live mode should replace the fixture-oriented energy policy with TinyVAD while retaining the same feature generator.
- **Partially resolved — model accuracy:** replacing eight random calibration tensors with all 63 representative normalized log-mel tensors increased the FVP result from 3/63 to 38/63. Regeneration with the E8 `RTSS_HE_SRAM_MRAM` Vela configuration preserved 55/55 NPU delegation and the FVP result remained 38/63, showing that the platform scheduling change did not alter classification accuracy on this corpus. The fp32 checkpoint scores 36/63 on the same source corpus (`speech-app/tools/evaluate_checkpoint.py`), so the remaining errors are not primarily caused by Ethos-U quantization: the shipped 51-class spelling checkpoint systematically confuses several control words and has no trained `_unknown_` class. A model trained with the upstream 20-command-plus-`_unknown_` recipe is required for the intended command demo. FVP log: `speech-app/test/recordings/fvp-uart.log`.
- **Partially resolved — SDS 3.1 text-record limitation:** the installed `sds.schema.json` supports binary value-list scalars, PCM audio, and images, but has no UTF-8/string payload content type. `ModelOut.sds.yml` and the firmware now record numeric class IDs, confidence, logit, expected class, and pass/fail; FVP produced three validated 21-record files. Human-readable detected words remain on UART/console. Native variable-length text records would require an SDS schema/tooling enhancement.
- **Confidence threshold:** select using a development corpus distinct from the final acceptance corpus. No threshold is yet justified.
- **Accuracy target confirmation:** the proposed 90% live top-1 gate is an engineering target, not a claim about the upstream model on this board and microphone.
- **SDS asset storage:** decide whether PCM/SDS files may be committed to Git or must live in an artifact store because of size/privacy.
- **UART protocol details:** 115200-8-N-1 is proposed; confirm the DFP retarget port and desired baud after board configuration.

## CDA knowledge workflow

- **Process gap — CMSIS knowledge was not used consistently during initial implementation:** the CMSIS Developer Assistant knowledge base contains relevant project, CMSIS-Ethos-U, MLOps/Vela, SDS, FVP, and target-document guidance, but it was not systematically queried before the application was designed and edited. This contributed to the E8 hardware/Vela configuration not being validated early enough. For every CMSIS subsystem, run `knowledge_search` before design or modification, read the selected full entry with `knowledge_get`, and use `list_target_docs` plus `search_target_docs` for device-specific facts. Record the source and resulting requirements in `SpeechApp.md`, record unresolved gaps here, and validate generated artifacts against those requirements before building or testing. For the current MLOps flow, validation must include an explicit E8 `mlops.hardware.target`, the correct E8 NPU type/MAC count, the DFP-provided device-specific `vela.ini`, and compatible system/memory selectors.
- **Issue decision:** do not file this as a CDA defect based only on the initial omission because the knowledge and routing guidance were available. File a CDA issue if a reproducible `knowledge_search` query fails to route to the relevant CMSIS-Ethos-U/MLOps material, returns materially incorrect guidance, or the documented workflow cannot expose the E8 DFP Vela configuration. A project-local `AGENTS.md` checklist or stronger automatic knowledge-first enforcement would reduce recurrence.

Use `sdsio.log` as the first diagnostic gate: no log means VSI3 was not loaded or could not initialize; a log without the script/config/workdir header means initialization failed; a header without `Playback step` means the target did not exchange flags; a step without `Playback: AudioIn` means stream naming/configuration failed; and missing `Closed`/`Playback complete` entries identifies an incomplete target state machine. Correlate those entries with target `sdsInit`, periodic `sdsExchange`, `sdsOpen`/`sdsRead`/`sdsClose`, EOS and EOT behavior. The skill should distinguish CMSIS **Run** from debug launch behavior and diagnose generated `*.cbuild-run.yml`/target-set settings without assuming that the `SDS:IO:VSI` component loads the host script.
- **Speech-corpus qualification skill:** collect or import licensed multi-speaker recordings, validate format and metadata, prevent speaker/class leakage, create positive/negative splits, and produce accuracy, rejection-rate, and confusion-matrix reports.

Any new skill shall pin tool/model versions, link authoritative sources, state its supported target and pack versions, and include a reproducible validation procedure. Do not treat the general Moonshine Voice skill as a substitute for the Moonshine Micro export skill.
